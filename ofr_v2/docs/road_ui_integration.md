# 도로망 최적화 UI 연결 — 2026-10-03

2026-10-05 비용 기본값과 저속 운송을 수정했다.
[현재 운송 조건](transport_upgrade.md)에 선택 입력·야간 복귀·가정 휴식 노드·
세전 밴 거리비와 견적 성분을 기록한다. 아래 100 USD 등 당시 값은 현재 기본값이 아니다.

사용자가 기존 디자인을 크게 바꾸지 않는 UI 확장을 승인했다. 기존 네 단계,
사이드바, 색상, 카드·표 구성을 유지한다. 현장 통행 제한·하역장·휴식 허가의
추가 수집/승인 절차는 이번 프로젝트 범위에서 제외한다. 해당 값은 시나리오
가정으로 기록하고 운영 준비 false를 유지한다. 배포·main 병합·최종 발표는 별도다.

## 추가 입력과 기본값

- 새 입력은 출발 창고 후보와 차량 대수다. 기존 예산·재고·품목 부피·단가·
  공급 한도·이용률·체류일수 및 물류 품목 조건을 계속 사용한다.
- 기본 창고: Przemyśl Lwowska 36. 저장된 공식 도로 선형에서 두 후보 중
  Medyka 10.269 vs 13.124km, Korczowa 35.151 vs 37.239km로 더 짧다.
  Dorohusk는 204.943 vs 204.560km로 차이가 약 0.4km여서 공통 출발 후보로
  선택했다. 실제 운영/용량 우위의 결론은 아니다. 공식 시청 공지 URL은 시설 목록에 있다.
- 기본 차량 1대: 최소 운행 자원부터 대수를 늘려 비교하기 위한 기준이다.
  실제 보유 대수나 최적 대수로 추정하지 않는다. 간편 입력은 1~3대다.
- 차량은 Ford Transit 350 L3 H2 FWD 디젤 밴의 공식 범위 제원에 근거한다.
  [Ford 25.5MY 공식 제원 PDF](https://www.ford.co.uk/content/dam/guxeu/uk/documents/brochures/cars/BRO-transit_van_25.5MY.pdf)
  10·12·13번 페이지(0부터 셈)를 확인했다. 총중량 3500kg, 보수적 공차 2190kg,
  기사 75kg를 반영해 화물 1235kg, 모델 공차 2265kg이다. 최대 화물 부피
  11.5m³, 높이 상한 2.530m, 미러 포함 폭 2.474m를 사용한다. 범위의 보수적
  조합으로 특정 실차/옵션 구성이나 구호기관 공식 추천 차량을 뜻하지 않는다.
- 품목 중량·조달·기한·폐기 조건은 기존 입력을 유지한다. 합성 예시 버튼으로만
  시험값을 채우며 제조사/구호기관의 공식 물품값으로 표시하지 않는다.

## 간편 배차 시나리오

`data/roads/ui_preset.json`에 출처·제원 계산·설정과 선정 이유를 보존한다.
평균속도 60km/h, 운행당 100 USD + km당 1 USD, 통행료 0, 상·하차/회차
각 30분은 프로젝트 가정이다. 창고·도착지에서 하역과 별개로 기사 휴식이
가능하다고 가정한다. 도로는 양방향/제한 없이 열려 있다고 가정하며 공식
기관의 통행 허가로 표현하지 않는다. 기존 보수적 기사 운전·휴식 제한은 유지한다.

배차 시작은 예측 기준주의 다음 월요일 00:00, Europe/Warsaw다. 근무창은
월~금 08:30~21:30, 출발 후보는 월·목 09:00이다. 날짜마다 폴란드 시간대의
UTC 차이를 계산해 써머타임 전후에도 09시 출발을 유지한다. 주 수요/재고
버킷은 기존 모델처럼 168시간 단위이고 정밀한 일별 소비 일정은 아니다.

간편 UI는 차량별 최단거리 도로 경로(k=1)를 구해 그 범위 안에서 트럭·적재·
출발 후보를 공동 계산한다. 다중 경로/더 많은 출발 시각은 기존 상세 road_network
JSON 방식으로 가능하다. 다중 경로와 많은 동일 차량의 조합은 기존 발주 변수
한도를 넘거나 30초/목적함수 단계 안에 최적성을 입증하지 못할 수 있다. 간편
프로필은 경로/시각 범위를 명시해 줄인다. 모델 한도/휴식 제약을 풀거나 시간 제한
결과를 최적이라고 표시하지 않는다. 시험한 3대의 물품 계획도 기존 한도 안에서 계산된다.

## API와 호환

`GET /road-options`는 가벼운 창고 목록·차량 제원·기본 시나리오를 반환한다.
`POST /optimize`에 기존 필드와 다음 값을 추가한다:

```json
{"road_planning":{"warehouse_id":"przemysl-lwowska-36","truck_count":1,"reference_date":"2026-01-26"}}
```

이 모드의 logistics에는 품목·재고·조달·기한·폐기 공통 필드만 전달한다.
서버의 `road_planner.py`가 저장된 공식 원문/주소에서 그래프를 만들며 HTTP
요청으로 도로를 재다운로드하지 않는다. 최신 창고–구호소 한 쌍만 캐시해
메모리를 제한한다. UI는 수십만 간선 JSON을 업로드/보관하지 않는다.
응답은 기존 계획/요약에 truck_plan과 road_scenario를 포함한다.

road_planning을 생략한 API, 기존 주별 노선 JSON, 명시적 road_network JSON은
그대로 동작한다. UI 상세 JSON 업로드는 도로 모드 목적지를 검사하며 기존
주별 노선 전용 검사가 도로 입력을 거부하던 문제를 수정했다. 과거 로컬 저장
물류 입력에 mode가 없으면 기존 주별 모드로 읽는다. 예측 모델·홀드아웃은 변경하지 않았다.

## 결과와 보관

트럭 운행별 물(L)·식량(1일분)·위생키트/담요(개), 적재 kg/m³, 출발·도착·복귀,
왕복 km를 표시한다. 모든 시각은 Europe/Warsaw로 변환한다. 운행을 선택하면
원본 GUGiK 구간의 모든 좌표를 SVG로 투영하고 배송/복귀 경로를 전환한다.
배경지도·실시간 교통을 추가하지 않았고 단절 구간을 직선으로 그리지 않는다.
휴식 이벤트는 별도로 표시한다. 운행이 없으면 빈 계획의 가능한 원인과 부족량
확인을 안내한다. 날짜를 바꾸면 기존 예측 갱신 흐름을 계속 사용한다.

중복 실행을 막고 계산 중 상태를 표시한다. 단계가 바뀌면 본문 맨 위로 이동한다.
큰 도로 결과는 브라우저 메모리에만 두며 로컬 저장소에는 입력/예측을 유지한다.
새로고침하면 계획 화면에서 재계산한다. 기존 주별 결과 저장 방식은 유지한다.
